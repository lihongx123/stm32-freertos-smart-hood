# STM32 参数与技术学习手册

更新：2026-10-01。阅读入口：`Core/Inc/app_config.h`、`Core/Src/`、`SensorTelemetry.ioc`，以及 [DMA 定位报告](dma_renode_diagnosis.md)。

## 1. 从字节到控制

USART1 接收 → DMA 循环内存 → IDLE/HT/TC 回调读取 NDTR → 提取新窗口 → SPSC 环形缓冲 → FromISR 通知 CommTask → 帧解析 → 共享快照 → SensorTask → 类型化队列 → ControlTask。

中断只搬运字节和通知；解析、状态切换、日志留给任务。DMA 内存解决外设搬运，软件 ring 解决任务调度造成的消费延迟，两者职责不同。

## 2. 接收与系统参数

| 配置 | 当前值 | 设置理由与改变影响 |
| --- | --- | --- |
| MCU / 时钟 | STM32F103C8T6；HSI 8 MHz | 固件与 Renode SysTick/TIM1 同步，避免超时尺度失真 |
| USART1 | PA9 TX、PA10 RX；115200、8N1 | 与注入协议一致 |
| DMA | DMA1_Channel5，循环、字节、内存递增、高优先级 | 连续接收，配合 HT/TC 和 IDLE 排空 |
| DMA RX 内存 | 256 B | 半满128 B提供搬运时机；扩大降低事件频率但增加缓存和部分场景等待 |
| 软件 ring | 512 B，实际511 B | 留一个槽区分满/空；满时计数并拒绝字节 |
| 帧缓存 | 96 B | 限制解析规模；超长丢至换行重新同步 |
| DMA/USART IRQ 优先级 | 5 | 符合 FreeRTOS FromISR 调用限制；同优先级避免生产者互相抢占 |
| APP_UART_RX_IT_FALLBACK | 0 | 默认 DMA；值1为单独的 IRQ 功能测试构建 |
| FreeRTOS heap | 生效值12288 B | 任务、队列等动态对象；要查最终宏，不只看早期3072定义 |
| APP_SIMULATION_TEST_HOOKS | 1 | 接受模拟任务停滞注入命令 |

理想115200/8N1字节率约11520 B/s，256 B约22.2 ms、半缓冲约11.1 ms。这是线路容量估算，用于理解服务时限，不是 Renode 实测时延。

## 3. 任务参数

栈单位为32位 word，字节数应乘4。配置与创建位置见 `Core/Src/` 的任务实现和 `freertos.c`。

| 任务 | 优先级 | 栈words | 作用 |
| --- | ---: | ---: | --- |
| Comm | 4 | 384 | 优先排空输入、解析帧 |
| Sensor | 3 | 256 | 周期发布传感快照 |
| Control | 3 | 384 | 执行状态机和风量/照明逻辑 |
| Fault | 2 | 256 | 超时、队列与健康故障检查 |
| Monitor | 1 | 512 | 心跳、栈/堆与运行日志 |

| 应用参数 | 当前值 | 意义 |
| --- | --- | --- |
| 周期 | 100 ms | 周期任务节奏，vTaskDelayUntil 减少累计漂移 |
| 健康检查 | 250 ms | 监测频率与开销折中 |
| 输入超时 | 2000 ms | 容忍短暂间隔，持续无有效输入进入故障 |
| 任务超时 | 1500 ms | 检测逻辑任务停滞 |
| 恢复 | 连续10个控制周期 | 约1秒，避免状态反复抖动 |
| 队列 | 4条 | 缓冲短突发；扩大可能让控制处理陈旧数据 |
| 烟雾阈值 | 100/300/600/850 | OFF/LOW/MEDIUM/HIGH/BOOST 分档 |
| 逆风阈值 | dp ≤ -10 | BOOST与WARNING |
| 暗光阈值 | light < 30 | 开灯逻辑 |

这些控制阈值是模拟场景设置。改成实际传感器时，应先确定量纲、标定与噪声范围，再设计阈值和滞回。

## 4. 协议和错误处理

输入：`S,smoke,temp,hum,light,dp\n`。整数范围依次为0..1000、-40..125、0..100、0..1000、-1000..1000。
支持分段输入、多帧连续输入；非法数值、NUL、超长帧拒绝并重新同步。
测试命令 `T,task_index,milliseconds\n`，任务索引0..3，最大5000 ms，用于制造任务停滞。

状态为 INIT、NORMAL、WARNING、FAULT、RECOVERY。故障位：传感超时1、非法帧2、通信超时4、队列溢出8、任务健康16。正常帧恢复后经过连续周期再退出 RECOVERY。

## 5. DMA 问题是怎么定位的

固定发送8、8、17、95、64、64、8字节，共264字节，每步核对内存、NDTR和累计搬运量。

| 累计输入 | 0 | 8 | 16 | 33 | 128 | 192 | 256 | 264 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 预期 NDTR | 256 | 248 | 240 | 223 | 128 | 64 | 256 | 248 |

发现两个模型问题：

1. 平台 TIM1 更新信号还接到 DMA Channel5，未发串口数据时就消耗计数、搬入零值。派生平台移除此 DMA 连线，保留定时器中断。
2. 原 DMA 模型 EN 位读回为false，在 HAL读取控制寄存器后错误关闭通道，表现为128字节附近停住。项目内派生模型修正使能读回。

固件 ELF 保持相同，修正模型后264字节全部匹配；默认 DMA 路径19/19场景通过。模型源和MIT许可保存在 `renode/`，具体哈希与实验见定位报告。

其他实际问题：模拟时钟与固件不一致、输入溢出后的帧同步、DMA重复位置/回绕计数。对应方法是校准时钟、丢弃损坏帧至边界、用实时NDTR和窗口游标只消费新增字节。

## 6. 资源结果与下一步设计

当前 text29388/data108/bss18772 B；data+bss=18880 B。场景最小剩余堆4176 B。
栈最小余量 Comm106、Sensor220、Control204、Fault92、Monitor300 words。Fault余量相对较少，新增局部数组或调用层级前要复测。

重新设计时优先考虑最新快照覆盖语义、硬件独立看门狗与故障输出策略、输入时间戳、栈保护。增大heap或ring会挤占20 KiB RAM，应先做总量预算。模拟验证关注软件链路，实际电气时序需要在对应平台测量。

## 如何学习与调整

先沿一条消息读完整链路，再改变一个参数，记录吞吐、延迟、内存和错误数。源码默认值、测试输入和测量结果是三类不同数据；增大队列不等于提高处理能力。本文的调整建议是设计分析，不代表已实施改动。
